# Server-only sensitive credentials
Objective: Keep saved credentials in the backend, expose status and explicit mutations rather than values, and safely retire sensitive browser storage.
Branch: fix/server-only-credentials; base: b18165de29293689a4fb9f24e42d746b98350bd9 (depends on PAT PR #161); delivery: feature-branch-chain; forecast: 1,200–2,000 authored lines; runner: scoped tsx Node tests plus focused Rust tests.
Trigger: risk items 1, 2, 3 (credential migration, security, shared IPC contracts). Scope in: webserver GitHub/provider/MCP secret boundaries, legacy browser migration, opaque cookie session safeguards. Scope out: Tauri/native implementation and verification (explicitly deferred), encryption-at-rest redesign, arbitrary command/file-content secret detection, unrelated UI preferences, publishing or merge. Rollback: revert each coherent implementation slice; never re-expose or automatically repopulate removed browser secrets. Success: public credential APIs/events never return stored values, authenticated backend operations still work, migration acknowledges persistence before browser cleanup.

## Specs

### S1 — Backend-only GitHub credentials [behavior]
> "necesito que datos sensibles se guarden en cookie https only que es lo mas seguro que tenemos a nivel de front?"
> "si esta perfecto"

The confirmation accepts the immediately preceding proposal: GitHub PAT, provider API keys and MCP secrets only on server; cookie only opaque access session; frontend configured/not-configured, replace/delete; safely clean existing sensitive browser copies and prevent downloading them again. Preferences remain local. This acceptance is not approval to disable HTTP localhost development or redesign encryption at rest.

- Saved GitHub PAT MUST NOT appear in viewer storage GET, save/update responses, events or status responses, for webserver clients. Native parity is explicitly deferred.
- Frontend MUST show configured state without receiving the saved value; replacement/removal MUST be explicit authenticated backend operations. GitHub list/clone/create and spawned Git MUST resolve saved PAT in backend, preserving existing no-PAT behavior.
- Transient newly entered credentials MAY be sent to backend over the existing authenticated transport, MUST NOT be written to browser storage and MUST be cleared after submission; backend errors MUST NOT echo secrets.
- **S1.1** Given a saved PAT, when a webserver client reads or mutates storage or receives events, then only configured status is exposed and no raw/encoded PAT is returned.
- **S1.2** Given a configured PAT, when GitHub list/clone/create or a new Git child runs without a client-supplied saved token, then backend uses its saved credential; frontend does not recover it.
- **S1.3** Given an existing PAT, when replacing, deleting or editing unrelated preferences, then explicit mutations take effect and unrelated edits cannot accidentally clear/replace the credential or return it.

### S2 — Safe legacy browser migration [behavior]
> "si esta perfecto"

- Legacy PAT/provider/MCP secrets MUST migrate only to an authenticated backend, without overwriting an existing backend secret.
- Browser copies MUST be deleted only after backend persistence/status confirms safe retention; failures MUST preserve the source for a later retry without logging values. New code MUST NOT repopulate those copies from read responses/events or persist fresh credentials through preview fallback.
- **S2.1** Given only a legacy local PAT, when migration succeeds, then backend holds it, browser copy is removed after acknowledgement and subsequent synchronization never restores it.
- **S2.2** Given migration failure or an existing backend PAT, when migration runs, then failure leaves local source intact and conflict keeps backend value; successful conflict acknowledgement permits local cleanup without overwriting backend.
- **S2.3** Given legacy provider/MCP mock storage, when import succeeds/fails/conflicts, then secrets are preserved on backend without overwrites, removed locally only after confirmation, and never newly persisted in mock fallback.

### S3 — Provider credentials and server discovery [behavior]
> "si esta perfecto"

- Provider API keys and all header values MUST remain backend-only in read/write responses. UI MUST expose names and configured status, allow replacement and explicit deletion; omitted/blank protected edits MUST preserve existing values and never save placeholder strings.
- Authenticated model discovery MUST run backend-side with saved credentials, without recovering credentials into the browser. Non-secret model/provider settings MUST remain editable.
- **S3.1** Given saved provider API keys/headers, when reading or upserting config through webserver, then values are not returned, omitted/blank edits preserve them, and explicit replacement/deletion changes only requested fields.
- **S3.2** Given a saved provider credential, when discovering models, then backend authenticates without returning or requiring the stored secret in the frontend.

### S4 — MCP protected maps and opaque URL/args [behavior]
> "Ocultar env/headers y usar referencias en URL/args"
> "Conservarlos y ocultarlos hasta reemplazarlos — recomendado"
> "URL y argumentos opacos en servidor — recomendado"

- All MCP env/header values MUST be backend-only. UI MUST show keys/configured status and support preserve, replace and explicit deletion without masked values becoming stored credentials.
- URL/args MUST also remain backend-only, returning configured status rather than saved values; full explicit replacement MUST be supported without recovering saved values. Runtime MUST use backend configuration unchanged. New reference syntax MUST NOT be added because Pi does not support interpolation in these fields.
- Existing URL/args values MUST remain operational and hidden until explicitly replaced; legacy values MUST NOT be downloaded, heuristically classified/transformed or automatically disabled.
- Web save MUST persist to backend, not report success after storing secrets in localStorage.
- **S4.1** Given saved env/headers, when a webserver client reads or edits MCP, then only keys/status return and preserve/replace/delete semantics hold per key.
- **S4.2** Given saved URL/args, when listing or explicitly replacing them, then prior values are never returned, omission preserves values, explicit replacement persists the new configuration and runtime still receives its backend configuration.
- **S4.3** Given legacy literal URL/args, when listing/editing unrelated settings, then values stay hidden and runtime behavior is preserved until explicit replacement.
- **S4.4** Given a web MCP save, when backend persistence succeeds/fails, then success is tied to real persistence and no sensitive localStorage fallback occurs.

### S5 — Opaque secure session cookie [existing]
> "si esta perfecto"

- The existing session cookie MUST carry only an opaque session identifier, not PAT/API/MCP secret values. HttpOnly and SameSite protections, expiry/logout/revocation and Secure for configured HTTPS/proxy deployments MUST remain enforced.
- HTTP localhost development MUST NOT be silently broken. HTTPS deployment documentation MUST explicitly cover Secure configuration; do not trust arbitrary forwarded headers to grant security.
- **S5.1** Given authenticated HTTPS/proxy configuration, when issuing, expiring and revoking a session, then cookie protections and backend lifetime rules hold and no application credential is stored in it.
